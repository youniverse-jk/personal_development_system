# PRODUCT_INTENT.md

# 人生存档 · 个人成长养成助手

**项目类型：** Android 横屏个人成长养成应用
**开发方式：** Vibe Coding（AI 辅助开发）
**目标用户：** 个人自用
**MVP 测试设备：** 红米 Note 14 Pro+，Android 16
**产品风格：** Galgame 视觉小说 × 温馨生活养成
**核心原则：** 本地优先、简洁实用、渐进开发

### 版本术语

- 本文中的“第一版”“第一阶段”和“MVP”均指第 12 节定义的第一个可运行版本。
- 第二阶段及第三阶段功能不属于 MVP，除非后续明确调整范围。
- 尚未确定的规则应标记为“待确认”，开发时不得自行补充。

## 1. 产品愿景

本项目旨在将现实生活中的学习、成长、娱乐、休息、消费和个人兴趣转化为具有游戏体验的个人养成系统。

用户在游戏中扮演现实中的自己，通过完成现实任务获得经验、提升技能、管理生活状态，并以游戏化方式观察个人成长。

产品尤其关注两个问题：

1. **时间感知较弱：** 用户容易在无意识刷手机时失去对时间流逝的感知。
2. **成长反馈不明显：** 学习与完成现实任务的过程缺少即时反馈，难以直观看到长期进步。

因此，产品的核心目标不是强制自律，而是：

> 让用户像经营游戏角色一样经营自己的现实生活，通过可视化、任务反馈与行为提醒，提高时间觉察和行动自主性。

### 产品设计原则

- 游戏中的角色代表现实中的用户。
- 游戏成长与真实生活行动相联系。
- 娱乐、休息与学习都是合理的生活活动。
- 不使用严厉惩罚机制制造焦虑。
- 优先实现实际功能，避免过度设计。
- 不必在 MVP 中实现全部长期规划功能。

## 2. 整体视觉与交互设计

### 2.1 屏幕方向

采用 **16:9 横屏游戏主界面**。

参考《重返未来：1999》等横屏游戏的界面组织方式，借鉴其层次感、角色中心布局、简洁功能入口和高级视觉气质，但不复制具体素材、图标或完整界面。

### 2.2 美术风格

采用以下组合：

- Galgame 风格的剧情对话框和选择按钮。
- 温馨生活养成游戏的氛围。
- 简洁、精致、易阅读的卡片式 UI。
- 米白、暖棕、低饱和蓝灰等柔和配色。
- 细边框、轻透明面板和适度留白。

避免复杂特效、过度装饰和拥挤布局。

### 2.3 主角形象

主角是用户自己的原创 BJD 娃娃风格二次元形象。

人物外观参考：

- 深棕色齐肩短发。
- 左侧齐刘海，中间有一缕较长头发搭在鼻子上
- 右侧无头发遮挡，眉眼较明显。
- 左侧具有独特鬓角发束。
- 红色镜框眼镜。
- 棕色眼睛。
- 真实 BJD 娃娃质感，而非明显的 AI 插画质感。

人物可以更换服装、姿势及场景，但第一版不需要开发独立的角色换装或骨骼动画系统。

MVP 的用户头像由用户从手机本地上传，并保存在应用本地。用户尚未上传头像时显示通用占位图，不在首次启动时强制用户选择头像。

MVP 的默认主界面底图使用 AI 生成的主角素材图，人物形象与整体画面应符合本节描述的外观和第 2.2 节规定的美术风格。默认底图作为应用内置资源提供，不在应用运行时调用 AI 生图服务。

## 3. 个人成长与等级系统

### 3.1 基础成长

角色拥有等级与经验值 EXP。首次启动时等级为 1，当前 EXP 为 0。

现实生活中的任务完成后获得经验。每个任务的 EXP 奖励由用户在创建任务时输入，允许范围为 0～500，包含 0 和 500。

例如：

| 行为               | 示例反馈 |
| ------------------ | -------- |
| 完成 Java 学习任务 | EXP +30  |
| 完成阶段学习关卡   | EXP +100 |
| 完成每日计划       | EXP +20  |
| 完成章节目标       | EXP +200 |

每一级升级所需 EXP 固定为 100。经验采用逐级累积方式：当前等级经验达到 100 后等级加一，并从当前经验中扣除 100；超出部分结转到下一级。一次任务获得的 EXP 可以触发连续升级多级，直到剩余经验小于 100。

数据层以“累计总 EXP”作为唯一持久化来源，等级与当前 EXP 根据累计总 EXP 计算，不分别保存可独立修改的等级和当前 EXP。完成任务与增加累计总 EXP 必须在同一个数据库事务中完成。

完成任务前必须弹出确认窗口。确认完成后：

- 任务立即变为已完成状态。
- 按创建时填写的数值结算一次 EXP。
- 完成状态不能撤销。
- 已完成任务不能编辑或删除。
- 不允许通过重复点击同一任务再次获取经验。

### 3.2 任务结构

MVP 只实现单层任务，不在第一阶段实现任务之间的层级、依赖或自动解锁关系。

MVP 中，每个任务至少包含：

- 任务名称。
- EXP 奖励值，由用户创建时输入。
- 完成状态。
- 创建时间及完成时间等必要的本地记录信息。

MVP 支持：

- 添加任务。
- 查看未完成及已完成任务。
- 完成未完成任务。
- 编辑或删除未完成任务。

任务一旦完成，不可撤销、编辑或删除。

以下三层任务结构作为后续版本的扩展方向：

**长期目标（主线）**

例如：完成 Java 后端技术学习，并独立开发项目。

**阶段任务（章节/关卡）**

例如：

- Java 基础
- MySQL
- MyBatis
- Spring Boot
- 项目开发
- 项目部署

**每日任务**

例如：

- 理解 Spring Boot 事务
- 完成一道 SQL 练习
- 学习英语单词 30 分钟

后续版本中，阶段任务可以设置前置关卡，完成条件满足后解锁下一阶段。长期目标、阶段任务和每日任务的详细关系及交互需在进入该版本前重新确认。

### 3.3 技能成长反馈

任务完成后，展示类似游戏通关的反馈：

「关卡完成！」

「学习了 Spring Boot 事务机制，对数据库事务的理解又加深了一些。」

「获得 EXP +50」

注意区分：

- **经验值：** 代表任务完成与行动积累。
- **技能掌握度：** 代表实际理解程度，可以通过复习或自测更新。

不能简单将学习时长等同于知识掌握度。

技能掌握度不属于 MVP。后续版本可以支持手动调整，不实现 AI 自动评估。

## 4. 角色状态系统

角色具有三个主要状态值，范围为 0～100，初始值均为 80。MVP 仅支持用户手动修改状态值，不根据任务、时间或其他行为自动推断或修改。

### 4.1 饱腹值

用于辅助记录饮食习惯。

MVP 只提供数值展示和手动修改。以下饮食记录能力属于第三阶段：

功能：

- 记录吃饭时间。
- 可记录食物名称。
- 吃饭后更新饱腹值。
- 支持用户手动修正。

饱腹值是游戏化的主观指标，不应当作医学或营养评估。

### 4.2 活力值

用于反映用户自我感知的精力状态。

MVP 只提供数值展示和手动修改。以下休息及睡眠记录能力属于第三阶段：

功能：

- 休息记录。
- 睡眠记录。
- 恢复活力值。
- 学习或活动后可调整活力。

不能单纯根据睡眠时长准确推断精力，因此应允许用户手动调整。

### 4.3 SAN 值

用于代表主观心理舒适度、精神负担及放松程度。

MVP 只提供数值展示和手动修改。不同活动的默认变化量及与生活记录的联动不属于 MVP：

功能：

- 娱乐活动可以帮助恢复。
- 压力较大的任务可能使 SAN 降低。
- 用户可以自行修正数值。
- 不同活动可以设定默认变化量。

不应机械规定学习一定降低 SAN、娱乐一定增加 SAN。

### 4.4 行为选择

本节属于第二阶段，不属于 MVP。

当 SAN 值较高时，可以提示：

「现在状态已经不错了，要不要开启下一项任务？」

提供：

- 开始任务
- 再娱乐一会
- 自由活动

**不强制禁止娱乐。**

状态系统是游戏化反馈，不应成为限制用户正常吃饭、休息或娱乐的依据。

## 5. 手机使用时间监测系统

这是产品最重要的辅助功能之一。

### 5.1 核心目的

帮助用户发现自己是否进入了无意识刷手机的状态，并逐渐建立对时间流逝的感知。

### 5.2 自动采集

Android 端使用系统提供的：

- `UsageStatsManager`
- `UsageEvents`

在用户授权使用情况访问权限后，读取 App 使用事件及时间戳。

根据应用前后台切换、屏幕锁定等事件，尽可能重建每个 App 的使用时间段。

需要考虑系统事件缺失、Activity 切换、多窗口、锁屏、跨日和系统权限等情况。

不假设所有安卓设备都能提供完全准确的连续记录。

### 5.3 24 小时时间轴

按日期展示 00:00～24:00 的使用情况。

每个 App 的使用区间以彩色时间块展示。

例如：

- 09:00～09:30 B站
- 09:30～09:45 微信
- 09:45～10:10 小红书

点击时间块可以查看详细记录以及修改分类。

### 5.4 自定义标签

提供默认分类：

- 学习
- 娱乐
- 社交
- 其他

允许：

- 为整个 App 设置默认类别。
- 对单次使用记录覆盖默认类别。
- 自定义标签名称及颜色。

例如 B站默认是娱乐，但某段观看学习视频的时间可以标为学习。

系统只根据使用事件及用户设置分类，不声称可以自动识别具体观看内容。

### 5.5 时间统计

至少包含：

- 今日娱乐总时长
- 今日学习总时长
- 各应用使用时长
- 每日时间分布



## 6. Galgame 式行为觉察提醒

### 6.1 核心机制

当用户连续使用娱乐 App 达到设定阈值时，显示一条温和提醒。

例如：

「咦，已经过去 15 分钟了吗？」

「你现在是想继续放松，还是回到之前的任务呢？」

选项：

1. 继续娱乐（延后提醒）
2. 开始学习（打开任务页面）
3. 休息一下
4. 本次不再提醒

### 6.2 提醒规则

- 默认阈值为连续娱乐 15 分钟。
- 用户可以自定义提醒时间。
- 用户可以设置提醒间隔及冷却时间。
- 避免在短时间内频繁发送重复通知。
- 支持暂时关闭提醒。
- 用户主动选择娱乐时不进行惩罚。

优先使用系统通知。

第二阶段不要求强制弹窗覆盖其他 App，也不要求拦截应用。

### 6.3 技术限制

Android 对后台执行存在限制，因此不保证提醒精确到秒。

需要在可接受的电量消耗与提醒及时性之间取得平衡。

不能为了实现这一功能而默认申请无障碍服务或过度敏感权限。

## 7. 日程系统

提供简洁的日程记录功能。

用户可以：

- 添加今日计划。
- 设置任务预计开始时间。
- 查看当天任务。
- 标记完成。
- 关联成长任务。

日程系统不属于 MVP。后续实现时不需要复杂的日历同步、团队协作及自动排程。

## 8. 衣柜系统

衣柜是个人服装收藏与管理功能。

每件服饰可以记录：

- 图片
- 名称
- 价格
- 状态

衣柜系统不属于 MVP。进入第三阶段后，优先完成图片上传、服饰信息保存、列表查看、编辑删除。

不要将衣柜设计成复杂的 3D 换装系统。

## 9. 钱包记账系统

钱包用于记录现实生活的收支。

基本功能：

- 添加收入
- 添加支出
- 自定义收支类别
- 查看账单
- 统计月度收入和支出
- 查看余额

使用真实人民币金额，不采用虚拟金币替代。

后续可与衣柜、饮食记录联动。

例如：

购买衣服时，可以选择同步创建服饰条目。

记录午餐时，可以选择同步添加餐饮支出。

自动联动应获得用户确认，避免重复记账。

## 10. 数据存储与隐私

应用主要用于个人自用。

本节要求从第一阶段 MVP 开始执行。后续阶段新增的数据类型也必须遵循相同原则。

### 基本要求

- 数据优先保存在手机本地。
- 不需要注册登录。
- 不需要云服务器。
- 不需要广告 SDK。
- 不需要第三方用户行为分析。
- 不上传应用使用时间数据。
- 尽可能减少系统权限。

主要使用 Room / SQLite 进行持久化。

用户选择头像或底图后，应用将图片复制到应用私有目录，数据库只保存应用私有副本的路径。不长期依赖相册原文件或临时 URI，避免原图移动、删除或授权失效导致图片不可用。

### 权限原则

仅在对应功能需要时申请权限。

自动读取 App 使用数据需要用户手动授权使用情况访问权限。

不默认申请：

- 无障碍权限
- 通讯录权限
- 短信权限
- 精确位置权限
- 悬浮窗权限

不要求用户关闭系统安全防护。

### 数据安全

- MVP 支持本地数据导出与恢复，范围覆盖第一阶段产生的全部数据，并包含用户头像和自定义底图图片。
- 备份文件采用带格式版本号的压缩包，包含结构化数据和用户图片，方便后续进行数据格式迁移。
- 恢复备份时采用整体覆盖：恢复内容替换应用中现有的第一阶段数据，不进行合并。
- 恢复时先校验完整备份，校验成功后再执行覆盖；校验或恢复失败时保留原有数据，不允许留下只恢复一部分的状态。
- MVP 支持删除第一阶段产生的个人数据。
- 执行覆盖恢复或删除全部个人数据前，必须显示二次确认窗口；用户取消时不得修改任何现有数据。
- 删除全部个人数据后，任务记录及用户上传的图片数据被清空，应用恢复为等级 1、当前 EXP 0、饱腹值 80、SAN 值 80、活力值 80、通用占位头像和默认底图。固定用户名“郑雅雯”保持不变。
- 第二阶段加入手机使用记录后，支持单独清空使用记录。
- 读取失败时明确显示原因。
- 图片不存在时提供占位图。
- 不假设应用重新安装后数据仍然存在。

## 11. 已确认技术方案

MVP 采用纯 Android 原生架构：

**Kotlin + Jetpack Compose + Room**

主要组件：

- Kotlin
- Jetpack Compose
- UsageStatsManager
- Room / SQLite
- Android 通知系统
- 系统图片选择器
- 应用私有文件目录
- 系统文件创建与选择接口，用于本地备份导出和恢复

架构约束：

- 第一阶段不引入 React、WebView 或原生通信桥。
- Compose 负责全部页面绘制、状态展示和交互。
- Room 负责结构化数据持久化。
- 用户图片保存在应用私有目录。
- 界面状态与持久化数据保持单一数据来源，避免同一数据在多个层级分别维护。
- 任务完成状态更新与累计 EXP 增加必须作为同一个原子操作提交。

设备范围：

- MVP 以用户的红米 Note 14 Pro+、Android 16 作为承诺测试基线。
- 第一阶段不承诺旧版 Android、平板、折叠屏或其他厂商设备的完整兼容性。
- 主界面保持横屏，并使用弹性布局适应目标设备的实际屏幕比例和系统安全区域，不假设物理屏幕严格为 16:9。

不需要为个人单机应用搭建 WebView 前端、Spring Boot 服务器或其他网络服务。

## 12. MVP 开发优先级

### 第一阶段：可运行的养成游戏

实现：

1. Android 横屏应用。
2. 固定主界面 UI。
3. 固定用户名“郑雅雯”、通用占位头像及用户上传头像、初始等级 1、初始 EXP 0。
4. 饱腹、SAN、活力状态。
5. 内置默认主界面底图，以及从本地选择图片替换底图和恢复默认底图。
6. 单层任务的添加、查看、编辑、删除及完成；已完成任务不可撤销、编辑或删除。
7. 创建任务时输入 0～500 EXP，确认完成任务后只结算一次 EXP；每 100 EXP 升一级，溢出经验结转并允许连续升级。
8. 本地保存、导出、覆盖恢复及删除第一阶段数据；备份包含用户头像和自定义底图；覆盖恢复和删除全部数据前必须二次确认。
9. “任务”和“状态调整”入口可交互；“日程”“今日安排”“衣柜”和“钱包”以无状态提示的不可交互空壳按钮呈现。
10. Galgame 对话区域只完成静态视觉设计，不实现对话逻辑。

验收标准：

- APK 可以在红米 Note 14 Pro+、Android 16 上正常安装并运行。
- 关闭重启后数据不丢失。
- 修改角色状态后界面立即更新。
- 三项角色状态首次使用时均为 80，且只能由用户手动修改。
- 任务完成前出现确认窗口；确认后正确获得创建时填写的经验。
- 任务 EXP 只接受 0～500；每累计 100 EXP 正确提升一级，超出部分正确结转，单次奖励可以连续提升多级。
- 已完成任务无法撤销、编辑、删除或重复获取经验。
- 用户可以上传自己的底图。
- 用户可以上传自己的头像。
- 未上传头像时显示通用占位图，不强制首次启动上传。
- 用户名始终显示为“郑雅雯”，且没有修改入口。
- 首次启动时显示等级 1、当前 EXP 0。
- 第一阶段全部数据及用户图片可以导出、覆盖恢复及删除；覆盖恢复和删除前均出现二次确认。
- 取消二次确认后现有数据保持不变；确认删除后任务和用户图片被清空，等级、EXP、三项状态、头像及底图恢复为规定的默认状态。
- 无需联网运行。

### 第二阶段：手机使用觉察系统

实现：

1. 使用情况访问权限引导。
2. 自动读取 App 使用事件。
3. 24 小时时间轴。
4. 自定义学习与娱乐分类。
5. 每日时间统计。
6. 连续娱乐提醒。
7. Galgame 行为选择。
8. 内置日常对话及不同选项对应的预设回复。

验收标准：

- 授权后能够读取受支持的应用使用记录。
- 可以按日期查看时间段分布。
- 能修改某段记录的分类。
- 分类统计与时间段数据一致。
- 权限关闭时有明确提示。
- 达到提醒阈值后在系统允许的条件下触发通知。
- 用户可关闭及延后提醒。

### 第三阶段：生活管理扩展

实现：

1. 衣柜。
2. 钱包。
3. 饮食记录。
4. 睡眠与休息记录。
5. 每日复盘。

验收标准：

- 衣服照片和价格可以长期保存。
- 收支记录可编辑并正确统计。
- 生活行为可更新相关状态值。
- 第三阶段新增数据也可以随本地备份导出和恢复。

## 14. AI 编程助手协作约束

在 Vibe Coding 时，AI 编程助手应遵循以下规则：

1. 以本文档作为长期产品方向，不擅自添加复杂功能。
2. 开发前先确认当前阶段和目标。
3. 优先实现可运行的最小版本。
4. 保持代码结构清晰，方便后续增加模块。
5. 系统权限只按实际需要申请。
6. 对涉及个人隐私和本地数据的功能采取保守设计。
7. 不随意引入外部服务、付费 API 和不必要的依赖。
8. 所有重要操作都应有错误处理。
9. 每完成一个阶段，应进行构建和基本功能测试。
10. 对用户不熟悉的技术决策，用简洁语言说明原因。
11. 如需求存在歧义，先询问用户，不自行扩大范围。
12. UI 的代码应与底图资源尽量分离，以支持用户自行换图。

## 15. 最终产品体验目标

用户打开 App，就像进入一款属于自己的生活养成游戏。

主角是现实中的自己。

每天的学习是一段冒险，长期目标是一条主线，生活琐事成为角色成长的一部分。

当用户不知不觉沉浸在手机娱乐中时，助手会通过温和的提醒帮助其重新察觉时间，并提供选择，而不是责备。

**最终目标不是培养一个永远高效的游戏角色，而是帮助现实中的用户更清楚地感知时间、更主动地选择行动，并在长期生活中看见自己的成长。**
