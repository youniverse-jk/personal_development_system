# 人生存档 MVP 实施计划

本计划依据 `PRODUCT_INTENT.md` 与 `architecture.md`，只覆盖第一阶段 MVP。执行时一次只完成一个任务；每个任务通过测试并完成对应 Commit 后，才进入下一项。标记为“需要人工验收”的节点必须等待用户确认，不得自动继续。

## 1. 执行原则

- 优先采用垂直切片：每个切片尽量贯通 Compose UI、ViewModel、Repository、Room/文件存储和错误反馈。
- 先打通“创建任务 → 完成任务 → 获得 EXP → 重启后保留”的最小业务闭环，再扩展其他功能。
- 保持单 Gradle `app` 模块，不提前拆模块。
- 只创建 `player_state` 和 `tasks` 两张 Room 业务表。
- 简单 CRUD 不增加多余 UseCase、接口或抽象基类。
- 每次 Commit 前运行该任务要求的自动测试；测试失败不得提交。
- 不在本计划中实现第二、第三阶段功能。
- 人工验收以红米 Note 14 Pro+、Android 16 为准。

## 2. 任务顺序总览

```text
P0 原型入口与素材确认（人工）
  ↓
P1 Android 工程骨架
  ↓
P2 玩家状态持久化与主界面首屏
  ↓
P3 创建任务与任务列表
  ↓
P4 完成任务与 EXP 闭环（人工）
  ↓
P5 未完成任务编辑和删除
  ↓
P6 手动状态调整（人工）
  ↓
P7 头像导入
  ↓
P8 底图替换与恢复默认（人工）
  ↓
P9 导出备份
  ↓
P10 校验并覆盖恢复（人工）
  ↓
P11 删除全部个人数据
  ↓
P12 UI 整合、错误处理与真机适配（人工）
  ↓
P13 MVP 全量验收与 Debug APK（人工）
```

P2～P4 构成第一个最小端到端业务闭环。P7～P8 共用同一套私有图片存储，但分别验收，避免一次实现过多功能。P9～P11 分别处理导出、恢复和重置，不合并成一个大任务。

## 3. 分步实施任务

### P0：确认 UI 入口与项目素材

**开发目标**

在编码前消除唯一会造成主界面导航返工的问题，并确保默认素材不依赖 Downloads 绝对路径。

**实现范围**

- 只制作轻量线框或文字交互说明，不编写业务代码。
- 明确头像更换、底图更换/恢复、备份、恢复和删除数据分别从哪个主界面入口进入。
- 确认最终默认底图和通用头像占位图，或明确原型阶段允许使用临时资源、最终验收前替换。
- 将确认结果补充到产品或架构文档。
- 最终素材进入项目资源目录时必须确认可使用，不允许构建依赖本机 Downloads 路径。

**依赖关系**

- 无。
- P1 可以准备基础工程，但 P2 的正式主界面导航布局不得在本任务未确认时定稿。

**验收标准**

- 每项 MVP 操作都有明确且唯一的 UI 入口。
- 不增加 Product Intent 未要求的业务功能。
- 默认底图和头像占位图有明确来源及落盘计划。

**测试要求**

- 无自动测试。
- 通过线框走查确认所有 MVP 操作可达，空壳按钮仍不可交互。

**人工验收：需要**

- 用户确认入口布局和素材方案后才能结束本任务。

**建议 Git Commit**

- `docs: confirm MVP navigation and asset inputs`

**开发目标**

创建能够在目标手机启动的最小原生 Android 应用，为后续垂直切片提供稳定基线。

**实现范围**

- 创建单 `app` 模块 Kotlin + Jetpack Compose 工程。
- 配置 Room、Kotlin Coroutines、基础单元测试和 Compose 测试能力。
- 创建 `MainActivity`、应用主题、`AppContainer` 和最小导航壳层。
- 将应用固定为横屏，并正确处理系统安全区域。
- 关闭 Android 自动云备份或通过数据提取规则排除数据库及用户图片。
- 主界面暂时只显示可辨识的启动占位内容，不实现业务功能。

**依赖关系**

- 技术栈已确认。
- 不依赖 P0 的最终视觉稿，但不得擅自确定尚未确认的功能入口。

**验收标准**

- Debug APK 能构建并安装。
- 应用在红米 Note 14 Pro+、Android 16 上横屏启动且不崩溃。
- 工程中没有 React、WebView、网络后端或多 Gradle 业务模块。
- 自动云备份配置符合本地优先要求。

**测试要求**

- 运行 JVM 单元测试任务。
- 运行 Debug 构建和 Android Lint。
- 在目标手机执行一次安装、冷启动、旋转/返回和重新启动检查。

**人工验收：不需要单独停顿**

- Agent 提供构建结果和真机安装说明即可；如果无法连接目标手机，则明确记录为 P13 前的待测项。

**建议 Git Commit**

**实现范围**

- 实现 `GrowthCalculator`，由 `totalExp` 派生等级和当前 EXP。
- 实现 PlayerRepository、HomeViewModel、HomeUiState 和 HomeScreen。
- 显示固定用户名“郑雅雯”、等级 1、当前 EXP 0、状态 80/80/80 和通用头像占位图。
- 主界面先使用默认/临时底图；入口按 P0 确认的布局呈现。
- “任务”和“状态调整”可以先进入空页面；其他空壳按钮不可交互且无“后续开放”提示。

**依赖关系**

- 正式入口布局依赖 P0。

**验收标准**

- 首次启动展示正确默认值。
- 关闭并重启应用后仍读取同一条玩家记录，不重复创建。
- 等级和当前 EXP 不作为独立字段持久化。
- UI 只通过 ViewModel/Repository 读取数据，不直接访问 DAO。

**测试要求**

- `GrowthCalculator` 单元测试：0、99、100、150、500 EXP。
- Room instrumentation 测试：首次初始化、重复初始化和默认值。
- HomeViewModel 测试：Room 状态正确映射为 UI 状态。
- Compose 测试：固定用户名、等级、EXP、三个状态值可见。

**人工验收：不需要单独停顿**

### P3：创建任务与持久化任务列表

**开发目标**

完成第一个可写业务切片：用户可以创建任务，并在重启后继续看到该任务。

**实现范围**

- 实现 `tasks` Entity、DAO、TaskRepository、TaskViewModel 和 TaskScreen。
- 从主界面“任务”入口进入任务页面。
- 支持输入任务名称和 0～500 EXP。
- 对空名称、非数字 EXP 和越界 EXP 给出明确错误，不写入数据库。
- 成功创建后立即显示在未完成任务列表。
- 同一页面显示已完成任务区域，但此任务暂不实现完成操作。
- 采用简单稳定的默认排序并集中写在 DAO/Repository 中；无需提供用户自定义排序。

**依赖关系**

- 依赖 P2 的 Room 数据库和导航壳层。

**验收标准**

- 可以创建 EXP 为 0、100、500 的任务。
- EXP 小于 0、大于 500、格式非法或名称为空时不能保存。
- 创建成功后列表立即更新。
- 强制关闭并重启后任务仍存在。

**测试要求**

- TaskRepository 单元或 instrumentation 测试：有效创建和各类输入校验。
- DAO 测试：插入、查询及稳定排序。
- Compose 测试：表单校验、创建成功、列表显示。

**人工验收：不需要单独停顿**

**建议 Git Commit**

- `feat: add persistent task creation and list`

### P4：完成任务并获得 EXP

**开发目标**

打通 MVP 最重要的端到端闭环：创建任务、确认完成、一次性结算 EXP、刷新等级，并在重启后保持结果。

**实现范围**

- 增加任务完成确认窗口。
- 实现 `completeTask(taskId)` Room 事务。
- 事务内使用条件更新，只有未完成任务成功变为完成时才增加 `total_exp`。
- 返回 `rewardGranted`、`totalExp`、`level`、`currentExp` 和 `levelsGained`。
- 完成后移动到已完成区域并显示通关反馈。
- Home 页面通过数据库 Flow 自动更新等级和 EXP。
- UI 可防连点，但数据正确性必须由事务保证。

**依赖关系**

- 依赖 P3。

**验收标准**

- 取消确认窗口时任务与 EXP 均不变化。
- 确认后任务只完成一次，并记录完成时间。
- 0 EXP 任务可以完成但不升级。
- 100 EXP 从等级 1 / EXP 0 变为等级 2 / EXP 0。
- 150 EXP 变为等级 2 / EXP 50。
- 500 EXP 可以连续提升 5 级。
- 对同一任务重复调用完成操作不会再次增加 EXP。
- 重启应用后完成状态和经验结果不变。

**测试要求**

- `GrowthCalculator` 边界及连续升级单元测试。
- Room transaction 测试：完成状态和 EXP 同时成功或同时失败。
- 重复调用及并发调用测试：同一任务只结算一次。
- Compose 测试：确认、取消、完成反馈和首页 EXP 更新。
- 目标手机手动完成至少一个跨级任务并重启验证。

**人工验收：需要**

- 用户验收“创建任务 → 完成 → 获得 EXP → 首页更新 → 重启保留”的完整闭环。
- 验收通过后再继续 P5。

**建议 Git Commit**

- `feat: complete tasks and award EXP atomically`

### P5：编辑和删除未完成任务

**开发目标**

补齐单层任务管理，同时确保已完成任务不可变规则在数据层生效。

**实现范围**

- 支持修改未完成任务的名称和 EXP。
- 支持删除未完成任务。
- DAO 更新和删除都带 `is_completed = false` 条件。
- 已完成任务不显示编辑、删除或完成入口。
- Repository 收到针对已完成任务的调用时返回 `TaskAlreadyCompleted`。

**依赖关系**

- 依赖 P4。

**验收标准**

- 未完成任务可以编辑并在重启后保留。
- 未完成任务可以删除。
- 已完成任务不能通过 UI 或 Repository 编辑、删除、撤销、再次完成。
- 修改未完成任务奖励后，完成时使用修改后的奖励值。

**测试要求**

- Repository/DAO 测试：未完成任务编辑、删除成功。
- 已完成任务的编辑、删除和重复完成均失败且数据不变。
- Compose 测试：操作入口只在未完成任务出现。

**人工验收：不需要单独停顿**

**建议 Git Commit**

- `feat: manage pending tasks and lock completed tasks`

### P7：上传并持久化用户头像

**开发目标**

建立安全的私有图片导入链路，并先用头像形成完整切片。

**实现范围**

- 实现系统图片选择器接入。
- 实现 PrivateMediaStore、ImageImporter 和 MediaRepository 的头像流程。
- 将用户选择的图片复制到应用私有 `media` 目录。
- 数据库只保存相对文件名，不保存外部绝对路径或临时 URI。
- 更新数据库成功后再删除旧头像文件；失败时清理新文件并保留旧头像。
- 无头像或头像文件缺失时显示通用占位图。
- 对大图按实际展示需要安全解码，避免直接加载原始相机尺寸。

**依赖关系**

- 依赖 P2。
- 入口位置依赖 P0。

**验收标准**

- 取消系统选择器不会改变头像，也不显示错误。
- 选择有效图片后头像立即更新。
- 原相册图片被移动或删除后，应用内头像仍可显示。
- 重启后头像仍存在。
- 私有副本缺失时回退占位图，不崩溃。

**测试要求**

- 文件存储 instrumentation 测试：复制、替换、失败清理、缺图回退。
- Repository 测试：数据库更新失败时旧引用不变。
- Compose 测试：占位图和成功头像状态。
- 目标手机从系统图片选择器导入一张大图并检查内存和显示效果。

**人工验收：不需要单独停顿**

**建议 Git Commit**

- `feat: import and persist private avatar image`

### P9：导出完整本地备份

**开发目标**

将玩家状态、任务、头像和自定义底图导出为可验证的版本化 ZIP。

**实现范围**

- 实现 BackupManifest、结构化 `data.json` 和 ZIP 生成。
- manifest 至少包含备份格式版本和导出时间。
- 在 Room 只读事务中取得一致数据快照。
- 通过系统文件创建器选择导出位置。
- 备份包含当前存在的用户头像和自定义底图。
- 导出失败不修改应用数据，不保留应用私有临时文件。
- Personalization 与导出共享简单 Mutex，避免导出时图片被替换。

**依赖关系**

- 依赖 P5、P7、P8，确保所有需导出的 MVP 数据已存在。
- 数据管理入口依赖 P0。

**验收标准**

- 可以成功生成 ZIP 文件。
- ZIP 包含 manifest、结构化数据以及存在的用户图片。
- 没有自定义图片时仍能导出有效备份。
- 取消系统文件创建器不修改数据且不报业务错误。
- 写入失败时显示明确错误并清理临时内容。

**测试要求**

- BackupManager 测试：有图、无图、多个任务和写入失败。
- 解包检查 manifest 版本和数据字段。
- 目标手机导出备份，并使用文件管理器确认文件存在。

**人工验收：不需要单独停顿**

**建议 Git Commit**

- `feat: export versioned local backup`

### P10：校验并覆盖恢复备份

**开发目标**

实现不会破坏现有数据的完整覆盖恢复流程。

**实现范围**

- 通过系统文件选择器选择备份。
- 实现 `inspectBackup`：检查 ZIP 结构、版本、JSON、字段范围、任务状态和必要图片。
- 校验通过后显示备份摘要和二次确认。
- 用户确认后再次校验并执行覆盖恢复。
- 先在私有临时目录准备图片，再在单个 Room 事务内替换两张表的数据。
- 数据库提交成功后才清理旧图片和临时目录。
- 不支持合并恢复。

**依赖关系**

- 依赖 P9。

**验收标准**

- 取消文件选择或二次确认时现有数据完全不变。
- 有效备份可以恢复玩家状态、任务、头像和底图。
- 恢复后等级和当前 EXP 由恢复的 `totalExp` 正确派生。
- 损坏 ZIP、未知版本、字段越界、任务状态矛盾或图片缺失时拒绝恢复。
- 任一步失败时保留恢复前数据，不出现半恢复状态。
- 恢复完成后重启应用，数据仍正确。

**测试要求**

- BackupValidator 测试：有效备份、损坏 ZIP、未知版本、非法数据、缺失媒体。
- Restore instrumentation 测试：完整覆盖、取消、事务失败和文件失败回滚。
- 端到端测试：创建数据并导出 → 修改当前数据 → 恢复 → 与导出时状态一致。
